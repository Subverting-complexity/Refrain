## Source and derivation notes

- Master used: a hand-assembled combination of `assets/logo/svg/logo-transparent.svg`'s
  icon + wordmark, with `id="icon"`/`id="wordmark"` added to their groups so the
  generator script could extract them as separate marks (that source file itself wasn't
  modified). Full text preserved in `master.svg` in this directory.
- Brand color: `#7edbb8` (matches `theme.accent` in `src/theme/index.ts`), not
  auto-detected — the source's icon is a gradient, so "the brand color" is a judgment
  call; this is the app's actual accent color.
- Background colors: light = `#f2faf7` (matches the existing `logo-light.svg` panel
  color), dark = `#111d1f` (matches `theme.background` / the app's splash and Android
  adaptive-icon background color in `app.json`).
- This directory supplements, and does not replace or overwrite, the hand-authored
  sources in `assets/logo/svg/` and `assets/logo/png/`, or the files `app.json` actually
  points at in `assets/images/`. Those keep shipping the app; this kit is the fuller
  brand-asset set (every size, format, color variant, and platform derivative) for
  everything else — docs, store listings, marketing, favicons, social profiles.
- Three related bugs in the shared `logo-variations` skill script
  (`~/.claude/skills/logo-variations/scripts/generate-logo-set.mjs`) were found and
  fixed while generating this set, since they'd have silently produced wrong output for
  any gradient-colored logo run through the skill, not just this one:
  1. Extracting a named group (`--icon-selector`/`--wordmark-selector`) dropped the
     source's `<defs>` block, so a group whose color came from a `url(#gradient)`
     reference rendered completely blank (no error, just an empty PNG) once isolated
     from its master.
  2. The mono-black/mono-white/single-color raster fallback (`rasterMonochrome`) treats
     any sufficiently light pixel as an intentional "cutout" to erase — correct for a
     genuine light-element-on-dark-shape logo, but it misfired on this logo two
     different ways: a solid pastel wordmark with no darker counterpart came out
     entirely blank, and the icon's own gradient (which spans light to dark within one
     continuous stroke) came out fragmented, with the lighter half of the stroke erased.
     The script now distinguishes three cases explicitly: a genuine literal light+dark
     hex mix uses the cutout heuristic, a gradient/pattern-colored mark flattens every
     opaque pixel to the target color directly (no cutout logic), and anything else
     (a single flat color, dark or light) gets a real vector recolor.
  3. `lockup-stacked` (a raster composite of the icon and wordmark marks, with no SVG of
     its own) always fell back to the raw pixel-luminance heuristic regardless of how
     its two source marks were classified, hitting the same fragmentation bug as #2.
     It now inherits its color classification from the master SVG's actual colors
     instead of guessing from pixels alone.
- Small-size check (skill step 4.6): rendered `icon-only` at 24px and looked at it — the
  loop and curl detail both stay legible, no simplified redraw needed.
